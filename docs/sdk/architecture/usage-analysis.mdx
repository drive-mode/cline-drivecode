# SDK usage analysis

Internal audit of how this monorepo consumes the Cline SDK packages (`@cline/sdk`, `@cline/core`, `@cline/agents`, `@cline/llms`, `@cline/shared`, `@cline/drive`). Goal: map real usage intensity, spot thin or bypassed surfaces, and call out beneficial features that are under-leveraged.

## Verdict

Product hosts already lean hard on **`ClineCore`** — not the lightweight `Agent` API. Session lifecycle, hub wiring, providers, tools/approvals, events, MCP, telemetry, auth, compaction, and modes are first-class across CLI, VS Code, Hub, and Desktop.

The gap is not “are we using the SDK?” — we are. The gap is **uneven depth**: multi-agent teams (defaults now aligned via D1 / Phase 2; VS Code still needs honest UI), programmatic automation (`cline.automation` vs Hub schedules — D2 documented), production cost abort beyond CLI env, OpenTelemetry depth (SDK adapter + shared env; VS Code still dual-stack), and remote backend mode.

## Package consumption pattern

| Package | Product hosts | Examples / evals |
|---------|---------------|------------------|
| `@cline/core` | Primary import surface (CLI, VS Code, Hub, Desktop, Menubar) | `cline-core-cli-agent`, menubar |
| `@cline/shared` | Types, `createTool`, prompts, hooks contracts, Drive types | Demo fixtures, examples |
| `@cline/llms` | Provider settings, catalogs, handlers (esp. VS Code) | Menubar catalog lookup |
| `@cline/drive` | Hub webview Drive kernel | — |
| `@cline/sdk` | **No direct product imports** | Quickstart, cli-agent, code-review-bot, multi-agent |
| `@cline/agents` | **No direct product imports** (runtime lives behind `ClineCore`) | Via `@cline/sdk` in Agent examples |
| Evals | Shell out to CLI / Harbor — behavioral coverage only | — |

`@cline/sdk` re-exports `@cline/core` (`sdk/packages/sdk/src/index.ts`). Product apps correctly import the package that owns the concern (`@cline/core` / `@cline/llms` / `@cline/shared`) rather than the umbrella. That is fine for in-monorepo hosts; external integrators are steered to `@cline/sdk`.

```txt
External docs / examples  →  @cline/sdk  →  @cline/core (+ agents/llms/shared)
Product hosts in-repo     →  @cline/core / @cline/llms / @cline/shared / @cline/drive
```

## Consumer ranking (SDK API depth)

1. **CLI** (`apps/cli`) — richest config + runtime composition: hub/local routing, spawn/teams (non-YOLO), hooks bridge, plugins as slash commands, schedules, MCP wizards, connectors, telemetry/feature flags, enterprise prepare hook.
2. **Desktop sidecar** (`apps/examples/desktop-app/sidecar`) — broadest product-like surface on hub backend: chat lifecycle, pending prompts/steer, checkpoints, MCP, marketplace, connectors, schedules, OAuth, session DB, child-agent listing.
3. **VS Code** (`apps/vscode/src/sdk`) — deep `ClineCore` adapter with host overrides (terminal, diffs, MCP hub, VS Code LM). Multi-agent explicitly disabled; browser automation stubbed; events translated to legacy webview messages.
4. **Cline Hub** (`apps/cline-hub`) — hub daemon + session/provider/schedule/MCP bridges; richest `@cline/drive` consumer in the webview.
5. **Menubar** — hub observer/launcher (`HubUIClient` / `HubSessionClient`), not a full runtime host.
6. **Examples using `Agent`** — teach the lightweight surface; not how product hosts run.
7. **Evals** — exercise tools/providers indirectly via CLI; zero direct SDK imports.

## What we use the most (and where)

### 1. Session orchestration via `ClineCore`

Composition roots:

- CLI: `apps/cli/src/session/session.ts` → `ClineCore.create`
- VS Code: `apps/vscode/src/sdk/vscode-session-host.ts` → local backend
- Hub: `apps/cline-hub/src/server/hub.ts`
- Desktop: `apps/examples/desktop-app/sidecar/context.ts` → hub `require-hub`

Common APIs: `start`, `send`, `abort`, `stop`, `dispose`, `restore`, `readMessages`, `subscribe`, `pendingPrompts.*`, compaction state helpers.

### 2. Provider / model / auth stack

Deepest in VS Code (`cline-session-factory.ts`, `provider-migration.ts`, `model-catalog/*`, `vscode-lm/*`) and CLI (`main.ts` + `ProviderSettingsManager`). Desktop and Hub expose catalog/save/OAuth command bridges. This is one of the strongest leverage areas already.

### 3. Tools, policies, approvals

Hosts inject `RuntimeCapabilities.requestToolApproval`, tool policy maps, and (CLI/VS Code) host-specific executors. VS Code is the outlier: it suppresses built-in `run_commands`, wraps editor/apply_patch for diffs, and bridges MCP through legacy `McpHub` rather than SDK MCP settings tools.

### 4. Events → UI translation

Every product UI has an adapter that maps `CoreSessionEvent` / `AgentEvent` into host messages (TUI, gRPC webview, Hub WS protocol, desktop chat chunks). This is necessary but means SDK event types are rarely the public UI contract.

### 5. Hub topology

CLI, Hub, Desktop, and Menubar treat hub discovery / `HubSessionClient` / `HubUIClient` / schedule services as core infrastructure. VS Code deliberately stays local-only for the extension host session.

## Config depth: enough, or room for more?

### Already richly configured

- Provider identity, keys, base URLs, regional/Bedrock/Vertex/SAP/Ollama specifics (especially VS Code)
- System prompt composition + workspace metadata
- Tool auto-approve / policy maps
- Plan/act mode + mode-switch tool
- Checkpoints enabled
- Compaction strategy (when auto-condense on)
- Telemetry + distinct IDs + extension context
- Hub client identity (`clientType`, `displayName`, cwd/workspace)

### Commonly defaulted or lightly exposed

| Knob | Situation | Opportunity |
|------|-----------|-------------|
| `maxIterations` | Product default 50 via `resolveProductSessionFeatures` + `applyDefaultMaxIterations` (SDK-5.1); host UI overrides still uneven | Surface overrides in VS Code settings / CLI args (BL-5.5–5.6) |
| `maxTokensPerTurn` / temperature / thinking | Set when user/provider supplies them | Cost-control presets by task type |
| `enableSpawnAgent` / `enableAgentTeams` | Phase 2 / D1: hosts call `resolveProductSessionFeatures`; VS Code needs setting + honest UI | Finish VS Code product exposure |
| `pluginPaths` / `extensions` | Phase 4 D3: all product hosts inject on session start | Optional host-side filtering / override tests (BL-4.*) |
| `automation: true` / `cline.automation.*` | Unused in apps; D2: Hub schedules are product-canonical | Embedder-only path; no store merge (SDK-3.2 deferred) |
| `backendMode: "remote"` | Unused | Only if remote runtime productizes |
| `ToolPresets` (`act`/`plan`/`search`/`minimal`/`yolo`) | Mode/yolo paths use policies; presets under-documented in hosts | Prefer Core presets over host-copied policy maps where possible |
| Resource / websocket policies | Hub uses `resolveResourcePolicy` for transport | Broader sandboxes / resource profiles in CLI & Desktop |
| Mistake limit / loop detection | CLI strong; VS Code wires mistake-limit callback | Share CLI defaults across hosts |
| Hub `ClineCore.create` telemetry / hooks / compaction | Telemetry + compaction on Hub Chat; host AgentHooks omitted (file hooks via daemon) | Optional host AgentHooks bridge (BL-6.2); Desktop compaction parity (BL-6.5) |
| OpenTelemetry via `loadOpenTelemetryAdapter` / shared env | SDK-8.1: hosts use `createConfiguredTelemetryHandle`; shared config accepts `OTEL_*` + `CLINE_OTEL_*` | Optional unify VS Code legacy stack (BL-8.1); production-guide env note (BL-8.3) |

**Bottom line:** we are past “minimal SDK wrap.” Configuration is deep for providers, tools, session identity, plugins-on-session, and shared session feature defaults. Remaining room is mostly **VS Code multi-agent UI honesty, usage-budget abort beyond CLI, VS Code OTEL dual-stack cleanup, and situational remote/gateway paths**.

## Features advertised but underused

From SDK docs / skill references vs app code:

1. **`ClineCore.automation`** — docs: `automation: true` then `cline.automation.start()`. Apps implement routines via `HubScheduleService` / desktop schedule commands instead (D2: product-canonical).
2. **Multi-agent teams as first-class product path** — Core exports `spawn_agent` plus `TEAM_TOOL_NAMES`. Phase 2 wires D1 defaults via `resolveProductSessionFeatures`; VS Code still needs setting/UI honesty.
3. **Programmatic plugins on the session** — **Done (Phase 4 / D3)** for CLI, Hub, Desktop, VS Code via `pluginPaths` + workspace `extensionContext`.
4. **Direct `Agent` + `createTool` for embedders** — well covered by examples; intentionally not the product-host path.
5. **LLM gateway (`DefaultGateway` / `createGateway`)** — documented for direct model access; hosts stay on `ClineCore` / `ProviderSettingsManager`.
6. **`backendMode: "remote"`** — documented; no product host uses it.
7. **Production cost abort patterns** — **Partial (SDK-5.2):** CLI one-shot `CLINE_MAX_SESSION_COST`; Hub/Desktop/VS Code/interactive still open (BL-5.1–5.4).
8. **Full hook coverage** — VS Code wires TaskResume; TaskError/SessionShutdown are wontfix; PreCompact/Notification + rebuild `isResume` remain backlog (BL-7.1–7.2, BL-7.9).
9. **Hub runtime depth** — Hub Chat now attaches telemetry + session compaction (SDK-6.1/6.2). Host `AgentHooks` intentionally omitted (file hooks via Core hub-daemon bootstrap; Desktop parity).
10. **OpenTelemetry** — **Partial→Done incremental (SDK-8.1):** shared env fallback; VS Code legacy stack remains (BL-8.1). Event projection shared layer **Deferred (SDK-8.2)**.

### Docs / skill drift (maintenance)

Skill references and Mintlify guides must track Core exports (`DefaultToolNames`, `TEAM_TOOL_NAMES`, `spawn_agent`). Plugin-only tools (e.g. agents-squad `start_subagent`) must be labeled as plugins, not Core builtins.

## Beneficial features to leverage next

Prioritized by product leverage (not calendar estimates). Ordering reflects dependency risk and user-visible upside.

### High leverage

1. **Align multi-agent defaults across hosts** — **Done (Phase 2 / D1)** for helper wiring; finish VS Code setting + UI honesty.  
2. **Unify scheduling on one SDK story** — **Done (D2 / SDK-3.1):** Hub `schedule.*` / CLI / Desktop are product-canonical; `cline.automation` is the embedder path. Docs + skill aligned; no store merge (SDK-3.2 deferred).

3. **Inject installed plugins into session config** — **Done (Phase 4 / D3).**

4. **Expose iteration / token budgets in host settings** — **Partial (SDK-5.1–5.2):** shared `maxIterations` default applied; usage abort on CLI one-shot only (BL-5.*).

5. **Bring Hub `ClineCore.create` up to CLI/VS Code depth** — **Done (SDK-6.1–6.3):** Hub Chat telemetry + compaction on create/start; host AgentHooks omitted by design (file hooks on hub daemon).

### Medium leverage

5. **Complete VS Code hook coverage** — **Done (SDK-7.1):** TaskResume wired; remaining kinds are wontfix/backlog (see integration build Phase 7).  
6. **Align OpenTelemetry with SDK adapter** — **Done incremental (SDK-8.1):** shared `OTEL_*`/`CLINE_OTEL_*` env; host stacks unchanged. Optional VS Code legacy unify (BL-8.1).  
7. **Resource policy profiles beyond Hub websockets** — sandbox / resource profiles for CLI Desktop long-running agents.  
8. **Reduce dual-path translation debt** — **Deferred (SDK-8.2):** hub `projectSessionEvent` is transport-only; VS Code/Hub/Desktop UI translators stay host-owned.

### Lower / situational

9. **`backendMode: "remote"`** — only if a remote execution product lands.  
10. **Direct gateway usage** — only for non-agent tooling (evals, model probes); product chat should stay on `ClineCore`.  
11. **Browser automation** — currently stubbed in VS Code SDK adapter; revisit only if browser tools return to Core builtins.

## Architecture notes (gotchas)

- **Product = `ClineCore`; examples = often `Agent`.** Do not infer product capabilities from `apps/examples/quickstart` or `multi-agent`.
- **VS Code is an adapter layer**, not a thin SDK client. Host overrides for terminal, diffs, MCP, and LM are intentional; built-in SDK behavior is not always what runs. `@cline/agents` is declared in VS Code `package.json` but unused in source.
- **MCP split brain:** CLI/Hub use Core MCP settings-file tools; VS Code sets `disableMcpSettingsTools: true` and injects tools via legacy `McpHub` + `createMcpTools`. **Keep adapter** per [SDK-7.2 spike](/sdk/architecture/vscode-mcp-spike).
- **Hub event protocols are hand-mapped.** Changing `AgentEvent` shapes requires updating CLI TUI, VS Code translator, Hub `agent-events.ts`, and Desktop `handleAgentEvent`.
- **Evals do not import the SDK.** Behavioral regressions in Core tools show up via CLI smoke/Harbor, not unit-style SDK construction in `evals/`.
- **`@cline/drive` is first-class but not on the `@cline/sdk` re-export tree** — Hub imports it directly; CLI Status uses `@cline/shared` (+ demo adapters), not `@cline/drive`.
- **Core subpaths matter:** `@cline/core/hub`, `@cline/core/hub/daemon-entry`, `@cline/core/telemetry` are public host surfaces beyond the root export.

## Summary

We use the SDK **enough for a full product runtime** — especially session, providers, tools, hub, MCP, and telemetry. We do **not** under-use the basic agent loop.

The highest-value remaining gaps are **VS Code multi-agent UI honesty**, **usage-budget abort beyond CLI one-shot**, and **optional VS Code OTEL dual-stack cleanup**. Phases 0–8 closed shared defaults, plugins-on-session, Hub depth, VS Code hooks/MCP honesty, and incremental OTEL env alignment.
