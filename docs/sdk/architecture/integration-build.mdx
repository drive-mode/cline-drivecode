# SDK integration build

**Public SDK:** [docs.cline.bot/sdk/overview](https://docs.cline.bot/sdk/overview) — `npm install @cline/sdk` (Node ≥22). Same harness as Cline IDE/CLI: plugins, checkpoints, MCP, cron, subagents, and more.

**Visual plan (primary):** Tldraw canvas `giaumqy8` — package map, leverage heatmap, decision diamonds D1–D4, phase strip, agent swimlanes, kickoff order.

**Companion detail:** task acceptance criteria below (and [Usage analysis](/sdk/architecture/usage-analysis)).

**Monorepo SDK version policy:** Product hosts and examples resolve `@cline/*` via `workspace:*` (always the packages under `sdk/packages/`). This tree is synchronized to upstream SDK **0.0.75** at Cline commit `61b95a62e`; the Drive-only `@cline/drive` package remains versioned in lockstep with `@cline/{sdk,core,agents,llms,shared}`. Do not pin numeric `@cline/*` versions inside this monorepo. Keep package `version` fields in lockstep via `sdk/scripts/version.ts` when cutting releases.

Turns usage analysis into a sequenced build against the **advertised public SDK**. Phases are ordered by dependency — **no calendar estimates**. Each **agent task** is one focused PR.

**Source of truth for symbols:** code (`DefaultToolNames`, `TEAM_TOOL_NAMES`, `spawn_agent`, `ClineCore` APIs) + [public docs](https://docs.cline.bot/sdk/overview).

## North star

Product hosts stay on **`ClineCore`**. Success means:

1. Hosts share **one defaults story** for multi-agent, plugins-on-session, budgets, and Hub runtime depth.
2. Public docs surfaces either **match product paths** or docs name the product-canonical alternative (esp. scheduling vs `cline.automation`).
3. An agent can pick any open task and land it without inventing product policy.

## Non-goals (whole build)

- Replacing host adapters (VS Code terminal/diff/`McpHub`, Hub WS protocol) with a thin SDK client.
- Adopting `backendMode: "remote"` or browser automation without a separate product decision.
- Rewriting evals to construct SDK objects (CLI/Harbor behavioral coverage is enough).

## Decision gates — LOCKED

| ID | Decision | **Locked** choice | Unlocks |
|----|----------|-------------------|---------|
| **D1** | Multi-agent host defaults | **CLI non-YOLO semantics** as product default: `enableSpawnAgent: true`, `enableAgentTeams: true` unless YOLO/sandbox/ACP special-cases. Hub Chat + Desktop adopt the same defaults. VS Code: expose a setting (default **on** once UI is honest); until then do not leave dead subagent UI. | Phase 2 |
| **D2** | Scheduling canonical path | **Hub `schedule.*` / CLI / Desktop routines** are product-canonical. Public scheduled-agents docs lead with that path; `cline.automation` is the embedder/SDK-local alternative. | Phase 3 |
| **D3** | Plugin session injection | Installed/enabled plugins load into `CoreSessionConfig` via `pluginPaths` / `extensions` + `extensionContext.workspace` on session start. | Phase 4 |
| **D4** | Cost budgets | Shared `maxIterations` defaults (+ optional usage abort helper); hosts may override via settings/UI. | Phase 5 |

Amend only by editing this table (and the visual plan). Agents must not invent alternate policy.

## Architecture note — MCP split brain (SDK-0.3)

| Host | MCP path |
|------|----------|
| CLI / Hub / Desktop | Core MCP settings file + install/OAuth helpers; settings tools available unless disabled |
| VS Code | `disableMcpSettingsTools: true`; tools injected via legacy `McpHub` + `createMcpTools` |

This is intentional adapter debt, not a one-line flip. **SDK-7.2 spike: Done — keep adapter** ([vscode-mcp-spike](/sdk/architecture/vscode-mcp-spike)). Do not enable VS Code settings MCP tools without a product migration.

## Phase 4 · Plugins on session

Installed/enabled plugins load into `CoreSessionConfig` via `pluginPaths` / `extensions` + `extensionContext.workspace` on session start (**D3**).

Core helpers (Phase 1): `resolveSessionPluginPaths`, `buildSessionExtensionWorkspace`, and async `resolveSessionPluginLoad`. Phase 4 adds the sync compose helper `buildSessionPluginInjection` that hosts prefer unless they already have loaded extensions. Core `local-runtime-bootstrap` still discovers plugins when the `"plugins"` config extension is enabled — hosts still pass `pluginPaths` + workspace so hub/remote/plugin `setup()` stay consistent.

## Phase 5 · Budgets

Shared `maxIterations` defaults (+ optional usage abort helper); hosts may override via settings/UI (**D4**).

### Agent task `SDK-8.2` — Event projection spike

| | |
|---|---|
| **Depends on** | — |
| **Owner surface** | Docs / backlog |
| **Goal** | Decide whether SDK/hub event projection helpers should be adopted by product hosts. |
| **Finding** | The only shared projector is hub-daemon `projectSessionEvent` (`session-event-projector.ts`) — it maps `CoreSessionEvent` → Hub WS `HubEventEnvelope` (already covered by hub boundary tests). It is **not** a UI projection helper. Product hosts each own protocol adapters by design: CLI TUI, VS Code `message-translator`, Hub Chat `agent-events.ts`, Desktop `handleAgentEvent`. There is no `@cline/shared` host-agnostic projector to adopt without inventing a cross-host UI contract. |
| **Decision** | **Deferred** — keep host translators; do not extract a shared product projection layer without a product UI-protocol decision. |
| **Tiny safe usage** | Hub daemon already uses `projectSessionEvent` (+ tests). No additional host wire. |
| **Status** | **Deferred** (documented; BL-8.2) |
